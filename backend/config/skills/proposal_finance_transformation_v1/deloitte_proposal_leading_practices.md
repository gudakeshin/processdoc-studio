# Finance transformation proposal — leading practices

Use when drafting or strengthening CFO-facing proposals (DOCX or narrative-for-PPTX). Patterns reflect common practice in large advisory proposals: problem-led story, quantified value, credible delivery, and explicit risk.

## Story arc

1. **Client situation first** — Open with the finance operating challenge (e.g. close length, forecast reliability, cost of finance FTE, control incidents), not firm history.
2. **Insight** — What is misunderstood or underestimated about the root cause (organization, data, technology, process, incentives).
3. **Hypothesis** — What you believe will move the needle, in one or two crisp sentences.
4. **What we will do** — Phased approach, decision points, and what the client must commit (data, SMEs, governance).
5. **Why us** — Evidence of comparable outcomes; keep proportional to the rest (not front-loaded).

## CFO-readable value articulation

Prefer **metrics the CFO already tracks**:

- Close calendar (workday-close, critical path tasks).
- Forecast accuracy / bias, scenario cycle time.
- Working capital (DSO/DPO/DIO) when relevant.
- Finance cost per revenue or per FTE, or GBS penetration.
- Control metrics (SOX issues, rework, manual journal rate) when relevant.

Anchor benchmarks with ranges or brackets if the user did not supply numbers; label them as **illustrative** or **[placeholder]**.

## Commercial hygiene

- Separate **outcomes** (business results) from **activities** (workstreams).
- Call out **dependencies** on client data quality, master data governance, and IT release calendars.
- Include a concise **risk register**: risk, impact, mitigation, owner — avoid generic “communication risk” only.

## Ten-section alignment

Map your 10-section framework explicitly in the outline so reviewers see completeness:

- Executive summary → client problem + headline outcomes.
- Client understanding → facts, benchmarks, constraints.
- Approach → phases, governance, decision gates.
- Solution / capabilities → what changes (process, org, data, tech) without boilerplate.
- Delivery → team shape, cadence, locations, PMO.
- Value / benefits → quantified where possible.
- Risks → specific to finance transformation.
- Case patterns → anonymized parallels, not credential stuffing.
- Commercial appendix posture → keep high-level in main body if user requests.

## Anti-patterns

- Generic “digital transformation” language without finance specificity.
- Value case with only cost takeout and no working capital / revenue / risk angle.
- Copy-paste “global network” paragraphs before the client problem is established.
